# 分格超级箱与超级缸

`CompartmentStorageRegistration` 在 GTOLib 中注册普通超级箱/缸各电压档和十种木材的 `1x2`、`2x2` 变种。ID 在普通机器 ID 后追加 `_1x2` 或 `_2x2`，例如 `gtceu:spruce_super_chest_2x2`。两格上下排列；四格从正面左上开始按行编号。

每格独立保存物品或流体及对应锁定类型。锁定开关、溢出销毁、自动输出、输出方向、输出面输入权限与容量上限由整个方块共享。总容量与同档普通版一致，容量上限设置整个方块的总量；各格均分，不能整除的余数依次分给前面的格子，以保持总量精确。降低上限保留已经存入的内容，超出上限时停止接收，启用溢出销毁时销毁新增溢出。

当前 GTM 依赖 `26.10.76` 的普通 ULV 超级缸注册容量为 0；其分格变种也保留 0。流体容量直接读取普通版 `TANK_CAPACITY`，如需调整普通 ULV 的容量，应在 GTM fork 处理。

右键小窗只向对应格存入；同一玩家在同一格连续右键可存入背包内同类物品或流体容器。左键取一个物品，潜行左键取一组；超级缸用容器接取。框架、分隔条或其他面可打开 GUI。点击 GUI 的存储图标选择下方状态面板显示的格子，配置按钮在各行展示但操作同一份配置。扩展朝向下的点击定位和渲染使用同一套模型变换。

合成：普通版加上下两片玻璃板得到 `1x2`；`1x2` 加上下两片玻璃板得到 `2x2`。输入要求无 NBT，防止合成时吞掉库存或锁定配置。需要先清空并使用未配置的机器。

控制器按格建立 key 索引；每个格子都有独立索引项，卸载与重连仍以方块为成员单位。管道、AE 和自动输出通过同一份分格库存访问。手持超级缸暴露对应数量的流体槽，与放置后的长整型容量和 NBT 格式一致。

模型基于 Functional Storage 的 `fluid_2.json`、`fluid_4.json`，沿用原木材、电压外壳和玻璃材质。来源、固定版本和 MIT 许可见 [素材清单](../src/main/resources/licenses/functional-storage-assets.md)。

玻璃只绘制各格的正面平面，外框、分隔条及内壁使用原机器外壳材质与连续的外壳 UV。`1x2` 使用 `overlay_screen_glass_16_32.png`，玻璃 UV 为 `[1,2,15,14]`，对应 32×16 纹理的 28×12 像素区域，与模型的 14×6 小窗保持相同比例。

`1x2` 发光装饰使用 `overlay_qchest_emissive16_32.png` / `overlay_qtank_emissive16_32.png`，每 8 tick 切换一帧。只截取各帧 `[20,4,28,12]` 的 8×8 图案，独立按正方形绘制，不再将发光图铺满玻璃。文字、装饰及状态图标共用独立的 84×36 像素显示区域，状态图标保持 16×16，数量居中；显示层前移并使用文字深度偏移，避免与玻璃互相遮挡。

流体直接按各格的边界绘制体积；物品等比缩放，数量文字和锁定/销毁图标在玻璃前单独等比绘制，不随长方形窗口压缩。

`CompartmentStorageGameTests` 检查全部注册变种的容量、模拟与实际存取、锁定空格、溢出、配置、世界及物品保存恢复、控制器逐格访问、各朝向的点击定位以及手持流体能力。验证使用 JDK 21，运行 `compileGametestJava`、`runGameTestServer`、`runData`、`spotlessCheck` 和 `buildGtolibProtected`。
