# 任务文本：清单、译文与官网修改的导入

任务书的文字在三处之间流动，每种数据只有一个主人：

| 数据 | 主人 | 流向 |
|------|------|------|
| 任务结构与中文原文 | 章节源码（`com.gtocore.data.quest`） | 图鉴导出时写出文本清单，随图鉴包进官网，只读 |
| 译文（英、日、俄、西、葡） | 官网数据库 | 官网机器翻译并经成员修订，下载成语言文件；仓库里的译文文件不手改 |
| 成员对中文原文的修改 | 官网只存"修改建议" | 管理员采纳后进入数据集，由导入工具写回章节源码；它带来的新行在官网先翻译，译文随同一个数据集下载 |

官网一侧的规则见官网仓库 `docs/domains/gamedata.md` 的「任务文字」一节。

任务文案只有中文原文能改：改意思、增删行、调整顺序都落在章节源码上。其他语言只有译文，行数和顺序跟着中文走，官网和导入工具都不接受给某种语言单独加行或删行。

## 文本清单

- 清单由图鉴导出写出，不进仓库，runData 不再生成它。官网的任务视图来自图鉴，图鉴每隔几个版本手动导出一次；清单跟着图鉴走，两边对应的才是同一版任务。
- 图鉴导出的探针在写完科技树和任务数据后调用 `QuestTextManifest.write(Path)`，每个难度、每种语言的导出目录（`gamedata-out-<语言>/`）里都有一份 `quest-text.json`。清单内容和语言无关，各目录里的是同一份，随图鉴包一起进官网。
- 清单只随完整版本的图鉴导出一起写出（2026-11-13 用户定）：任务文字不用更新得比图鉴更频繁，不单独导出清单，也不随 runData 生成。官网没有上传清单的入口。
- 只在开发环境能生成：清单要读章节源码，找不到源码目录或源码解析失败时不写，探针日志里记 `QUESTTEXT missing`。
- 清单是不带缩进的紧凑 JSON，行、章节、任务按固定顺序输出，同样的文字两次生成逐字节相同（`version` 字段除外）。
- 清单包含：
  - `schema`：清单格式版本，目前是 1。
  - `version`：整合包版本（`GTOCore.getPackVersion()`，和图鉴里的 `packVersion` 同一来源）。
  - `lines`：任务书的全部可翻译行（`gtocore.quest.*` 与界面文字 `gtocore.questbook.*`），每行带语言键、中文原文，以及各占位的样式（颜色、粗斜体、链接）。
  - `chapters`：章节 id、标题行的键、是否仅开发者可见。
  - `quests`：每个任务的标题、副标题、描述在源码里的形态，与游戏内编辑器读到的 `QuestEdits.TextEntry` 相同（`line` 带样式参数的 Java 写法，图片等是 `raw`）。
- 语言键以原文的 CRC32 结尾，原文一改键就变，旧译文自动不再生效；官网用同一算法（`QuestLine.keyOf`）算键。
- 进官网：清单随图鉴包装上，管理员在官网管理台「任务文字 → 文本清单」按「载入 <版本> 的清单」。官网收到新清单后，会把文字已进入游戏的已采纳修改标记为"已进入游戏"。代价是开发者在代码里新写的任务文字要等下一次图鉴导出才有译文。

## 导入官网数据集

管理员在官网管理台「任务文字 → 供游戏导入的数据集」下载一个 JSON，在本仓工作树里运行：

```powershell
.\gradlew.bat questTextImport "-Pdataset=<下载的文件>"
```

加 `-PquestTextCheck=true` 只检查不写入。工具不启动游戏，只用章节源码的语法模型。

- **文字检查**：原文修改里的每行文字和每条译文过同一套检查，不合格的不写入，报告里给出键（或指令）和原因。工具不启动游戏，而 GTOLib 的类在游戏之外加载不了（保护构建之后会抛 `UnsatisfiedLinkError`），所以占位与颜色码的判断在工具里自带一份，写法照 `QuestLine` 的；真正把关的仍是游戏：原文在 runData 构建时由 `QuestLine` 校验，译文占位对不上时游戏显示中文。
  - 不能为空或只有空白。
  - 不能含这些码位：U+0000–U+001F、U+007F–U+009F、U+200B–U+200F、U+2028–U+202E、U+2060–U+2069、U+FEFF（官网用同一范围）。
  - 不能带 `&` / `§` 颜色码（判断与游戏构建时相同）。
  - 占位的判断与游戏的 `QuestLine` 一致：`{…}` 片段与 `[item]`、`[itemTag]`、`[fluid]`、`[fluidTag]` 按出现顺序构成占位序列，`{}` 不能不成对或嵌套。原文修改要求占位数等于该行的样式参数数，译文要求占位序列与 `zh_cn` 原文完全相同。`%s` 之类不算占位（任务行不认它）。
  - 译文另查一道 `%s` 参数：`%s`、`%d`、`%1$s` 这类写法的个数和顺序要与原文相同（`%%` 不算，花括号里的不算）。界面文字（`gtocore.questbook.*`）靠它们填数值，少一个进游戏就错位。官网收译文时查的是同一条。
- **译文**写到 `src/main/resources/assets/gtocore_quest/lang/<语言>.json`（独立命名空间，原版会合并各命名空间的同名语言文件，不与 runData 生成的 `gtocore` 语言文件冲突）。保留的是通过上面检查、且键在 `zh_cn.json` 里或由本次指令带来的行；这些文件整份是下载产物，不手改。
  - **指令带来的新行**：成员改过的原文，键会变（键以原文 CRC32 结尾），新键在 runData 之前不在 `zh_cn.json` 里。官网在采纳修改时就按同一算法算出新键并先翻译，数据集里带着这些译文。工具在写入（或判为「已是目标内容」）一条指令时，按 `gtocore.quest.<章>.<任务>.<CRC32>` 算出它每一行的键，这些键的译文以指令里的文字为原文检查后一并写入。终端里每种语言一行写明其中有几行是新行。冲突或失败的指令带来的键不收。
- **原文修改**是一条条 `text` 指令（`QuestEdits.Op`，与游戏内编辑器写回源码用的是同一种），经 `QuestEdits.apply` 落到章节文件。每条指令带它写作时所依据的原文（`base`）：
  - 源码现状与 `base` 一致：写入。
  - 源码已是指令要的内容：记为"已是目标内容"，不动。
  - 源码现状两者都不是：记为冲突，**不写入**，报告里给出 `base`、`current`、`wanted` 三份内容，人工合并后在官网把该修改标记为已处理。
- 指令里的样式参数与 `raw` 调用必须已存在于源码现状中，否则拒绝：数据集不能把新代码带进仓库。只接受 `text` 类型。
- **全写或不写**：工具先算完全部指令和译文，再写文件；写入时先把每个文件写成同目录的临时文件，全部写好后再逐个替换。计算阶段出错时不写任何源码和语言文件。
- 结果打印在终端，并写入 `build/quest-text/import-report.json`。中途出错时报告照样写出，`error` 字段写明错在哪，`files` 是应改动的文件，`written` 是实际已写入的文件。只检查模式只写报告。
- 退出码：中止（数据集版本不符、源码解析失败、读写出错）为 1；有冲突或失败的指令为 2；全部成功为 0。

导入后的收尾由人（或代理）完成，工具不代劳：

1. 看 `git diff`，确认改动。
2. `compileJava`，再 `runData` 重新生成语言文件。
3. 等下一次图鉴导出：新清单随版本进官网，管理员载入后，已导入的修改标为"已进入游戏"，它带来的那些行直接是译好的行。

## 相关代码

- `QuestTextManifest`、`QuestTextImport`：`com.gtocore.common.quest.hot`，与热修改同包；引用了 `jdk.compiler`，只在开发环境使用。`QuestTextManifest.write(Path)` 由图鉴导出探针 `ProgressionExportProbe` 反射调用，写成功返回 true；导入工具是独立进程，直接由 Gradle 任务启动。
- `QuestLine.keyOf`、`QuestLine.bound`（按语言键取已绑定的行，清单用它取样式参数）：GTOLib。
